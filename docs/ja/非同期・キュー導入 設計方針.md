# 非同期・キュー導入 設計方針

> **位置づけ：** Lv（アーキテクチャレベル）が扱わない「負荷・信頼性」の軸について、キュー導入とパフォーマンス対策をどう扱うかの設計方針をまとめる。Lvと独立した「能力（capability）」としてKaachanの検査を有効にする型設計案も含む。**本ドキュメントは案であり、`src/` にはまだ反映していない。**

---

## Lvは何の軸か

Lv1〜10は「コード規模が増えたとき、人間とAIの認知負荷をどう抑えるか」の軸だ。ファイル数・ドメイン数・チームの人数が増えるにつれて段階的に構造を足していく。

一方、キュー導入やパフォーマンス対策は「トラフィック・処理時間・障害にどう耐えるか」の軸であり、コード規模とは独立している。

| | Lvの軸 | 負荷・信頼性の軸 |
|---|---|---|
| 問い | コードをどこに書くか | どう実行されるか |
| 増える原因 | 機能数・ドメイン数・人数 | ユーザー数・処理時間・外部依存の不安定さ |
| 例 | Logic層の導入、domain分割、CQRS | キュー、キャッシュ、読みレプリカ、リトライ |

Infra-Slimeの「欠点」で既に認めている通り、**Lv3でも100万ユーザーがいれば別の構成が必要**になる。逆にLv9でも社内ツールならキューは要らない。したがって「Lv8以上ならキュー」のようにLvへ紐づけることはしない。

---

## キューを入れても変わらないもの

Slime Architectureは、起動口の違いをWorkflowに知らせない作りになっている。

- **Parse層がHTTP境界を担う**ため、Workflowは「入力とプリンシパル」しか受け取らない。HTTPから来たかキューから来たかを知らない
- プリンシパルには既に `{ kind: "system"; job: string }` があり、キューワーカーはこれを渡す
- 進化論の「バッチ処理・非同期処理の起動口」で、起動口の選択はアーキテクチャの本体と切り離すと決めている

```ts
// HTTPの起動口
r.post("/orders", json(parsePlaceOrder, PlaceOrderWorkflow))

// キューの起動口（同じWorkflow・同じ形の入力）
export const handler = createLambdaHandler({ trigger: "sqs", parse: parsePlaceOrder, workflow: PlaceOrderWorkflow })
```

**Workflow / Logic / Store の置き場所と依存方向は変わらない。** キュー導入で「設計が大きく変わる」と感じる部分の大半は、層の構造ではなく次節の「実行の意味」の変化だ。

---

## キューを入れると変わるもの：実行の意味

### 1. 投入の確実性 — `defer()` から Outbox までの段階

`defer()` はコミット成功後に**同じプロセス内で**動く。プロセスがその瞬間に落ちれば副作用は消える。「失敗許容な副作用」には十分だが、「必ず実行されるべき後続処理」には足りない。信頼性の要求に応じて段階的に上げる。

| 段階 | 書き方 | 失われる場面 | 向いている処理 |
|---|---|---|---|
| 0. 同期 | Workflow内で直接呼ぶ | なし（失敗はリクエストの失敗） | 短く、失敗したら全体を失敗させたい処理 |
| 1. `defer()` | `defer(() => sendMail(...))` | コミット後〜実行前のクラッシュ | 分析・通知など失敗許容な副作用 |
| 2. `defer()` でキュー投入 | `defer(() => enqueue(event))` | コミット後〜投入前のクラッシュ | 重いが、まれに落ちても困らない処理 |
| 3. Transactional Outbox | `withTransaction()` 内で `outbox` に書く → relayが投入 | なし（DBに残る） | 決済後処理・在庫連携など必ず実行すべき処理 |

```ts
// 段階3：Outbox。業務データとメッセージを同じトランザクションで書く
return withTransaction(async () => {
  const placed = await orderDomain.placeOrder(input)
  if (!placed.ok) return placed
  await outbox(placed.value)   // ドメインイベントをそのままメッセージにする
  return placed
})
```

Lv8の**ドメインイベント（戻り値方式）**はそのままメッセージの型になる。`app/workflow.ts` がイベントを受け取り、「同期で呼ぶ / `defer()` / `outbox()`」のどれで後続へ渡すかを選ぶ。イベントのルーティングが `app/workflow.ts` を読めば全部わかる、という戻り値方式の利点はキュー導入後も保たれる。Lv7以前でキューを入れる場合は、ドメインイベントの代わりに `shared/` にメッセージ型を置く。

### 2. 冪等性

ほとんどのキューは「少なくとも1回」配信だ。同じメッセージが2回届く前提で書く。

- メッセージには**冪等キー**（メッセージID・イベントID）を持たせ、parseで必須項目にする
- Workflowは次のどちらかで冪等にする
  - **自然に冪等**：upsert、状態遷移の条件付き更新（`UPDATE ... WHERE status = 'pending'`）
  - **処理済み記録**：Storeに冪等キーを記録し、記録済みなら何もしない（記録は業務データと同じトランザクションで書く）
- 冪等性の判断は業務の判断なので、Workflow / Logicの責務とする。FWが一律に重複排除するのは補助にとどめる

### 3. リトライの判断 — エラーの2分類がそのまま使える

Slimeは既に「業務上の拒否（`Result` の err / `DomainError`）」と「技術的障害（throw）」を分けている。HTTPで4xxと5xxに分けているのと同じ基準で、キューではリトライ可否が決まる。

| Workflowの結果 | HTTPでは | キューでは |
|---|---|---|
| 成功 | 2xx | ack |
| 業務上の拒否（err / `DomainError`） | 4xx | **リトライしない**。ackして記録し、必要なら補償処理のイベントを出す |
| 技術的障害（throw） | 5xx | **リトライする**。上限を超えたらDLQ（処理できなかったメッセージの置き場）へ |
| parse失敗 | 400 | **リトライしない**。即DLQ（何度やっても同じ結果になる） |

業務上の拒否をリトライしても結果は変わらず、キューを詰まらせるだけだ。この分類をキュー起動口のアダプター（`createLambdaHandler` 等）がFWとして実装すれば、アプリ側は何も書かずに正しいリトライ挙動になる。

### 4. メッセージの形とバージョン

キューのペイロードも外部入力であり、**キューの境界でもParseを通す**。HTTPと違い、デプロイ時点でキューに古い形式のメッセージが滞留していることがある。

- メッセージ型に変更を加えるときは、旧形式も受け付けるparseを一定期間残す
- 破壊的変更はイベント型を分ける（`ORDER_PLACED` → `ORDER_PLACED_V2`）。`shared/events.ts` の型定義ルールはそのまま適用する

### 5. 順序と並行

キューの配信順序は基本的に保証されない。順序に依存する処理は、キー単位の順序保証（FIFOキューのメッセージグループ等）を使うか、状態遷移の条件付き更新で古いメッセージを無視する。「全体の順序」を前提にした設計は避ける。

### 6. HTTP応答

処理をキューへ回すルートは、結果ではなく「受け付けた」ことを返す。

```ts
// 案：応答形式に accepted を追加する。202 Accepted と状態確認用のURLを返す
r.post("/reports", accepted(parseCreateReport, RequestReportWorkflow))
r.get("/reports/:id", json(parseReportId, GetReportStatusWorkflow))
```

`json`・`stream`・`html`・`sse` と並ぶ応答形式の1つであり、Workflow以下は変わらない。結果整合になることをフロントエンドに伝える責務は、このルート定義が負う。

## パフォーマンスの扱い

パフォーマンス対策の大半は、層が正しく分かれていれば**Store・Client・インフラの中で局所的に**閉じる。これはSlime Architectureが提供する価値の1つとして明示してよい。

| 症状 | 直す場所 | Workflow / Logic への影響 |
|---|---|---|
| N+1 | Store（一括取得の関数を足す） | ループの中でstoreを呼ばず、一括取得の結果をメモリ上で突き合わせる。Kaachanの `store-call-in-loop`（💡）が候補を示す |
| インデックス不足 | Store（クエリ）・マイグレーション | なし |
| 読み取りが重い・越境JOINが多い | Store / Lv10の読みモデル | なし |
| 同じ外部APIを何度も叩く | Client（キャッシュ） | なし |
| DBロックが長い | `defer()` で非DB処理をトランザクション外へ | `app/workflow.ts` の書き方のみ |
| 1リクエストの処理が長すぎる | キューへ回す（本ドキュメント前節） | ルートの応答形式とWorkflowの冪等性 |
| 全体的に遅い | インフラ（スケールアウト・読みレプリカ・CDN） | なし |

方針は次の通り。

- **計測してから直す**。Slime FWのメトリクス自動計装で、どの層で時間を使っているかを先に特定する（`Slime FW詳細設計.md` 参照）
- **キャッシュはStore / Clientの内側に閉じる**。Workflowが「キャッシュから読むか」を意識し始めたら、それは層の漏れだ
- Workflow / Logicを書き換えないと速くならない場合は、たいてい「同期でやる必要がない処理を同期でやっている」ので、キューへ回すことを検討する

## Kaachan：能力（capability）軸の検査 — 型設計案

### 考え方

キュー関連の検査は「Lvが上がったら有効」ではなく、**コードにその能力が存在したら有効**にする。能力はプロジェクト設定で宣言するのではなく、Kaachanがコードから検出する。

| 能力 | 検出方法（例） |
|---|---|
| `queue` | キュー起動口がある（`createLambdaHandler({ trigger: "sqs" })`、FW組み込みのキューワーカー定義など） |
| `outbox` | `outbox()` の呼び出しがある |

棚上げした「Lvをテックツリーにする案」や「ドメインごとのレベルオーバーライド」とは違い、**Lvは一本道のまま残す**。能力はLvの横に立つ旗であり、選ぶ道ではなく、コードの事実から決まる。チーム内で「今どのLvか」の会話が複雑になることはない。

### 型の拡張案

`RuleDefinition` に `requires` を足す。`requires` がないルールは今まで通りLvだけで決まるので、既存のルールは変更不要だ。

```ts
// src/capabilities.ts（新規・案）
export type Capability = "queue" | "outbox"

// src/rules-catalog.ts（拡張案）
export interface RuleDefinition {
  readonly id: string
  readonly summary: { readonly ja: string; readonly en: string }
  /** レベルごとの重大度（昇順） */
  readonly severity: readonly SeverityStep[]
  /** このルールを有効にする能力。すべての能力がコードに存在するときだけ検査する。省略時はLvだけで決まる */
  readonly requires?: readonly Capability[]
}

/** 指定レベルで有効なルールとその重大度の一覧。capabilities を省略すると能力つきのルールは含めない */
export const getRulesForLevel = (
  level: ArchitectureLevel,
  capabilities: readonly Capability[] = [],
): readonly { readonly rule: RuleDefinition; readonly severity: Severity }[] =>
  RULE_CATALOG.flatMap((rule) => {
    if (!(rule.requires ?? []).every((c) => capabilities.includes(c))) return []
    const severity = getRuleSeverity(rule, level)
    return severity === undefined ? [] : [{ rule, severity }]
  })
```

能力つきのルールも `severity` はLvの段階で持つ。たとえば「キュー起動口がparseを通さない」は、Lv3でParse層を導入した後なら以降ずっとWarningにする、という表現ができる。

### ルール案

| id | 内容 | requires | 重大度案 |
|---|---|---|---|
| `queue-entry-parse` | キュー起動口がparseを通さずにWorkflowを呼んでいる | `queue` | Lv3〜 ⚠️ |
| `queue-idempotency-key` | キュー起動口のparseの出力型に冪等キーがない | `queue` | 全Lv 💡 |
| `queue-principal-system` | キュー起動口がsystem以外のプリンシパルを作っている | `queue` | Lv3〜 💡 |
| `defer-enqueue` | `defer()` の中でキューへ投入している（コミット後のクラッシュで消える。必ず実行すべきならOutboxを提案。opt-in） | `queue` | 全Lv 💡 |
| `outbox-outside-transaction` | `outbox()` を `withTransaction()` の外で呼んでいる（業務データと原子的に書けない） | `outbox` | 全Lv ❌ |

冪等性そのもの（Workflowが本当に冪等か）は静的には判定できない。Kaachanが検査するのは冪等キーが入力にあるかまでにとどめ、それ以上はAI向けrulesテンプレートの記述で補う。

### 生成物への影響

- `docs/ja/Lv別アーキテクチャリファレンス.md` の検査項目一覧には能力つきのルールを混ぜず、本ドキュメントに「能力別の検査項目」として生成する
- AI向けrulesテンプレートは、Lvのテンプレートとは別に `rules/_content/capability-queue.md` のような追加テンプレートとして提供し、能力が検出されたときに連結する

## Infra-Slimeとの関係

Infra-Slimeの推奨インフラ表は「Lv8+でキューサービス」としているが、本方針に合わせて**キューサービスの推奨はLvではなく `queue` 能力の検出で決める**のが整合的だ。`slime export:infra-context` にも、Lvとメトリクスに加えて検出された能力を出力する。

## 残課題

- **FW組み込みのキューワーカーの置き場所**：Lambda等の外部アダプターとは別に、FW内でワーカーを動かす場合の定義ファイル（`app/route.ts` に相当するもの）をどこに置くか
- **Outbox relayの提供範囲**：relay（outboxテーブルを読んでキューへ投入するプロセス）をFWが提供するか、プラグインにするか
- **補償処理（Saga）**：複数のキュー処理にまたがる業務の途中失敗をどう戻すか。`orchestrate/` はトランザクション専用としたので、非同期の調整役の置き場所は別に考える必要がある
- **`accepted` 応答形式の詳細**：状態確認リソースの形式、Problem Detailsとの整合
