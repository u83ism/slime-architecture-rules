## メトリクス自動計装

### 設計構想

Slime Architectureは「DBアクセスが必ずstore.tsを通る」「外部APIが必ずclient.tsを通る」「ユースケースが必ずWorkflowを通る」という構造をFWが強制しているため、各境界でFWが透過的にラップすることで、ユーザーが計測コードを一切書かずにメトリクスを取れる可能性がある。Laravelのクエリロギングと同じ発想だが、DB以外の境界（外部API・Workflow）もカバーできる点がSlimeの強み。

### 自動取得できるメトリクスのイメージ

| 境界 | 取得メトリクス |
|---|---|
| Workflow | 実行時間・成功/エラー率 |
| Store | クエリ時間・件数・スロークエリ検知 |
| Client | HTTPステータス・レイテンシ・タイムアウト率 |
| Parse | バリデーションエラー率 |
| Middleware | 認証失敗率・レートリミット発火数 |

### N+1の実行時検知

Kaachanの `store-call-in-loop` は「ループの中でstoreを呼んでいる」という構造しか見られず、ループが3回なのか1万回なのかは分からない。本当にN+1が起きているかは、Storeの自動計装で実行時に判定する。

- 1回のWorkflow実行（1リクエスト・1メッセージ）の中で、**同じstore関数が閾値（例：10回）を超えて呼ばれたら**警告ログを出す。store関数単位で数えるので、SQLの正規化は要らない
- 警告にはWorkflow名・store関数名・呼び出し回数を含め、`slime export:infra-context` のサマリーにも載せる
- 本番では件数の集計だけにとどめ、警告ログは開発環境とサンプリングされたリクエストに限る

インデックス不足も同様に静的には判断できないため、Kaachanでは扱わない。スロークエリ検知とEXPLAINの結果を材料として出力し、判断はAIエージェントと人間に委ねる。

### アーキテクチャレベルとの連動

アーキテクチャのLvが上がると自動計装の対象境界も増える：

- **Lv1-3**：Workflow単位のみ（WorkflowはLv2から存在する）
- **Lv4**：Store/Clientが分離されるタイミングでこれらも自動計装対象に加わる
- **Lv6以降**：ドメイン別のWorkflow/Storeが分かれるので、ドメイン別のメトリクスが自然に取れるようになる

### メトリクス転送先とコスト問題

アプリがメトリクスを直接CloudWatch等に送ると「API呼び出し数 × データ点数 = 莫大なコスト」になる。

#### OpenTelemetry（OTel）方式（メイン戦略）

現代的な解法は**OpenTelemetry（OTel）Collectorを間に挟む**ことで：
1. アプリはローカルのCollectorに投げるだけ（ほぼタダ）
2. Collectorが1分間分を集約・バッチしてから送信（API呼び出し数を激減）

Slime本体はOTel SDKを抱えて「ローカルのCollectorに投げる」までを担当し、Collector以降のルーティング（CloudWatch / Grafana / Datadog等）はプラグインとユーザー設定に委ねる：

```
Slimeアプリ → OTel Collector（ローカル） → [CloudWatch / Grafana / Datadog]
                                                 ↑ @slime/metrics-* プラグインで設定
```

バックエンドを後から差し替えられる・複数同時送信できる点もこの設計の利点。

#### CloudWatch EMF方式（AWSに閉じる場合の代替）

**CloudWatch EMF（Embedded Metric Format）**：CloudWatch Logsへの構造化JSON書き込みからメトリクスを自動抽出する仕組みで、PutMetricData APIより安くログとメトリクスを同時に取得できる。

#### 低レベル帯のデフォルト

低Lvでは「Stdoutに出すだけ（ファイルローテーションはOSのlogrotateやDockerのlog driverに任せる）」でも十分。OTel Collector接続はLv4以降でRepository/Clientが分離されて自動計装の恩恵が出始めるタイミングが自然な導入機会。

## Level間マイグレーション戦略

### 位置づけ

Slimeの最大の価値提案は「スムーズなアップスケーリング」だが、その中核機能となるLevelマイグレーションの実装難度が高く、詳細が未定。これがスライムたる所以（形を変えながら成長する）であり、**実現できれば差別化機能として最強だが、実装難易度がFW全体で最も高い可能性がある**。

### コマンドインターフェース

```bash
slime migrate --to-level 6    # Lv6に移行
slime migrate --dry-run       # 変更内容の事前確認（実ファイル変更なし）
slime level:next              # 次のLvのディレクトリ構造を確認
slime level:current           # 現在のLvを解析・表示
```

### 移行時に行うこと（概念的には明確）

1. 現在のファイル構造を解析してLvを判定
2. 移行先Lvのディレクトリ構造を生成
3. ファイルを移動
4. importパスを自動修正
5. 移動先が曖昧なファイル（どのdomainに入れるかなど）はインタラクティブに確認

### 最大の難所

**3〜5の「移動後に壊れる参照の自動修正」をどう実現するか**が最大の難所。方向性：

| 手段 | 内容 | 課題 |
|---|---|---|
| LSP（Language Server Protocol） | TypeScript Language Serverにimport解析を委ねる | LSPとの統合が複雑 |
| ts-morphによる静的解析 | AST解析でimportパスを書き換え | 動的import・型のre-exportに弱い可能性 |
| 組み合わせ | LSP + ts-morph両方使う | 実装コスト大 |

実装として成立するかは要検証。

### ドメイン分割時の曖昧ファイル問題

`slime migrate --to-level 6` でドメインを切る際、「このファイルはuserドメインかorderドメインか」をFWが自動判断するのは困難。対応案：

1. **インタラクティブCLI**：曖昧なファイルをリストアップし、一つずつユーザーに確認
2. **prefixヒューリスティック**：関数名のprefix（`userCan*`等）から候補を提示（確定はしない）
3. **AIコンテキスト出力**：`slime export:migrate-context` で曖昧ファイルリストをAI向けに出力し、AIと対話しながら決定

## ジョブ管理（バッチの依存関係）

> **位置づけ：** 案。`src/` にはまだ反映していない。起動口をどこに置くか（FW組み込みのcron・CLI・Lambda等）は進化論の「バッチ処理・非同期処理の起動口」で決めた通りアーキテクチャ本体と切り離す。本節が扱うのは、**スケジュールで動くジョブ同士の前提条件と、その運用の作法**。イベントで動くキュー処理は [非同期・キュー導入 設計方針](./非同期・キュー導入%20設計方針.md) が扱う。

### 問題意識：開始時刻が暗黙の前提になっている

中小Web系のSaaSでは、バッチの依存関係を管理できている所がほとんどない。よくあるのは「Aを2:00、Bを3:00に設定する。1時間あればAは終わるだろう」という**時刻による暗黙の依存**だ。cronやEventBridgeは時刻しか知らないので、依存関係はコードのどこにも書かれず、作った人の頭の中にしか残らない。その人が抜けると、どのバッチを止めてよいか誰も判断できなくなる。

業界では、この問題は昔から別の分野として解かれている。

| 層 | 代表例 | 依存関係の扱い |
|---|---|---|
| 大企業・SIer | JP1/AJS、Senju、Control-M 等のジョブ管理ツール | ジョブネットとして先行・後続を定義するのが当たり前。重く、高価 |
| データ基盤 | Airflow、Dagster、Digdag 等 | DAGで宣言する。データエンジニアの道具で、アプリのバッチとは担当が分かれがち |
| クラウドの部品 | Step Functions、EventBridge Scheduler | 書けるが、アプリのコードとは別の場所で管理される |
| アプリFW | Laravelの `Bus::chain`・`withoutOverlapping`、Spring Batch | キューのジョブの数珠つなぎや、1ジョブ内のステップは扱う。**スケジュールで動くジョブ同士の前提条件・業務日付・終了予定時刻**は標準では扱わない |

SIerの知恵は運用設計書や製品の中にあり、Web系の開発者には伝わってこない。Web発の軽量FWはリクエスト中心の文化で、バッチは「いつ動かすかはアプリの外（cron・k8sのCronJob）が決める」付け足しの扱いだった。困るのはバッチが数十本に増えた数年後で、その頃にはFWを選び直せない。

Slime FWでは、**ジョブ管理の基本的な作法を、コードの中の宣言とKaachanの検査で強制する**。

### SIerのジョブ管理から持ち込む概念

| 概念 | 中身 | Slimeでの形 |
|---|---|---|
| 起動条件と開始時刻を分ける | 時刻で起動するのは先頭のジョブだけ。後続は「先行ジョブが正常終了したら起動」 | `schedule()` は先頭だけ。後続は `job(..., { after })` |
| 終了予定時刻 | 「何時までに終わっていないと異常」を開始時刻とは別に持つ | `deadline`。超えたら通知する |
| 業務日付 | 「どの日の分の処理か」をシステム時刻とは別に持ち、ジョブに引数で渡す | 入力に必須。後続へ同じ日付を引き継ぐ |
| 稼働日カレンダー | 休日・月末・締め日などで動かす日を定義する | `calendar`（案） |
| 再実行の作法 | 異常終了したジョブから再開する、スキップして後続を流す | `slime job:rerun` / `slime job:skip`（案） |
| 排他 | 同時に動かしてはいけないジョブの組 | `exclusive`。同じジョブの重複実行は常に防ぐ |

### 宣言の形（案）

```ts
// app/jobs.ts（置き場所は案）
// 時刻を持つのは先頭のジョブだけ
schedule(CloseDailySalesJob, { at: "02:00", calendar: "businessDays", deadline: "04:00" })

// 後続は時刻を持たない。何に依存するかだけを宣言する
job(AggregateMonthlyReportJob, { after: [CloseDailySalesJob], deadline: "05:00" })
job(SendInvoiceMailJob,        { after: [AggregateMonthlyReportJob] })

// ジョブの定義。中身は入力とプリンシパルを受け取るWorkflowと同じ形
export const CloseDailySalesJob = defineJob({
  name: "closeDailySales",
  description: "前営業日の売上を締める",
  owner: "billing",
  parse: parseBusinessDate,          // 入力に業務日付を必須にする
  workflow: CloseDailySalesWorkflow, // 起動口はsystemプリンシパルを渡す
})
```

- 依存関係の宣言からDAGを組み、循環はFWの起動時（とKaachan）にエラーにする
- `description`・`owner` を必須にし、`slime job:list` / `slime job:graph` で一覧とDAGを出す。後続がなく、出力を読む者もいないジョブは「止めても安全かもしれない候補」として示す
- 実行履歴（業務日付・開始・終了・結果）をFWがDBに残す。再実行・deadline超過の判定・後続の起動はこの履歴を見る
- 起動口は差し替えられる。FW組み込みのスケジューラが既定で、`slime export:job-graph` でStep Functions等の定義に書き出す道も残す（後回し）

### バッチのWorkflowで変わること

層の構造（Workflow / Logic / Store）は変わらない。変わるのは実行の作法で、キュー導入と同じく既存の仕組みの延長で書ける。

- **業務日付は入力で受け取る**：Workflowの中で現在時刻から対象日を決めない。0時をまたいだ実行や翌日の再実行でも対象日がずれず、再実行が安全になる
- **1件ごとの失敗はResultで集計する**：1件の業務上の拒否でジョブ全体を止めない。結果を「成功◯件・拒否◯件」にまとめて履歴に残す。技術的障害（throw）はジョブの異常終了として扱い、後続を起動しない
- **トランザクションはチャンク単位**：ジョブ全体を1つの `withTransaction()` で包まない。ロックが長くなり、途中で落ちると全部やり直しになる
- **大量の読み込み**：storeの読み取り関数の4種類の形（IDで引く・一意キー・絞り込み・条件式の検索）に加えて、少しずつ流して読む形（カーソル・チャンク）が要る。5つ目の形として認めるか、ジョブからだけ呼べる形にするかは残課題
- **冪等にする**：再実行が前提なので、キューと同じく自然に冪等にするか処理済みを記録する（[非同期・キュー導入 設計方針](./非同期・キュー導入%20設計方針.md)の「冪等性」）

### Kaachan：宣言されていない依存の検出

Slime FWならではの強みはここにある。Lv6のテーブルの所有権により、Kaachanは**各ジョブのWorkflowがstore経由でどのテーブルに書き込み、どのテーブルを読むか**をコードから辿れる。そこから「ジョブBはジョブAが書くテーブルを読んでいるのに、Aへの依存が宣言されていない」を警告できる。Airflow等の外部ツールはジョブの中身を知らないので、これはできない。

キューと同じく、能力（capability）軸の検査として扱う。能力 `job` はジョブの定義（`defineJob`）があれば検出する。

| id | 内容 | requires | 重大度案 |
|---|---|---|---|
| `job-undeclared-dependency` | ジョブが、他のジョブの書き込むテーブルを読んでいるのに、そのジョブへの依存（`after`）を宣言していない | `job` | Lv6〜 ⚠️ |
| `job-dependency-cycle` | ジョブの依存関係が循環している | `job` | 全Lv ❌ |
| `job-schedule-on-dependent` | `after` を持つジョブにも時刻（`schedule`）を設定している（時刻による暗黙の依存の温床） | `job` | 全Lv ⚠️ |
| `job-business-date` | ジョブのparseの出力型に業務日付がない | `job` | 全Lv 💡 |
| `job-now-in-workflow` | ジョブのWorkflowが現在時刻を直接取っている（業務日付を入力で受け取る） | `job` | Lv3〜 ⚠️ |
| `job-whole-transaction` | ジョブのWorkflow全体を1つの `withTransaction()` で包んでいる | `job` | 全Lv 💡 |

Lv5以下ではテーブルの所有権の宣言がないので、`job-undeclared-dependency` はstore関数の中に現れるORMのモデル名から推定する程度にとどまる（opt-inのHint候補）。

### 範囲外

FWが責任を持つのは**1つのアプリの中のジョブ同士の依存**まで。次のものは外部ツールに任せる。

- 他システム・他サービスのジョブとの依存
- 「外部からファイルが届いたら動く」等、アプリの外のイベントを待つ起動条件
- 過去分の一括再実行（backfill）や、運用管理画面の作り込み
- 1つのジョブの中のステップの細かな再開（Spring Batchのような枠組み）。必要になったらジョブを分ける

### 残課題

- ジョブの宣言ファイルの置き場所と、Lv6以降でdomainをまたぐジョブの依存をどこに書くか（`app/` に置くのが自然か）
- 実行履歴テーブルの形と、複数サーバーで動かすときの起動の排他（Laravelの `onOneServer` 相当）
- ストリーム・チャンク読み込みをstoreの読み取り関数の形にどう加えるか
- 稼働日カレンダーの定義方法（祝日データの取り込みを含む）
- イベントで動くキュー処理（Lv8のドメインイベント・Outbox）と、スケジュールで動くジョブの境目。「ジョブの完了をイベントとして出し、キュー処理が受け取る」形を許すか

## Infra-Slime（構想）

> 💧Slimeはコードのアーキテクチャだけでなく、**インフラ構成もアプリのレベルに合わせてスケールさせる**という構想。「母ちゃんの言う通りにしておけばサーバーは落ちない」を実現するやつだ。

### コマンドとレベル対応表

```bash
slime eject infra --level 5  # 現在のレベルに最適なインフラ定義を吐き出す
```

| レベル帯 | 推奨インフラ構成 |
|--|--|
| Lv 1-3 | SQLite + シングルコンテナ（Docker Compose 1つ。VPS 1台で完結） |
| Lv 4-7 | PostgreSQL + Redis + アプリコンテナ（DBとアプリを分離。マネージドDB推奨） |
| Lv 8+ | マネージドDB + キューサービス + サーバーレス/k8s（クラウドネイティブ構成） |

このコマンドで、現在のレベルに最適な `Dockerfile` や `Terraform` / `CDK` のコードを生成する。アーキテクチャレベルとインフラ構成を対応させるという発想自体が既存のFWには存在しておらず、**「コードがスケールすればインフラもスケールする」を一気通貫で提供できる**のがSlimeならではの強みになりうる。

各クラウドプロバイダーごとに実装が大きく異なるため、コアFWには組み込まず **`@slime/infra-aws`・`@slime/infra-gcp`・`@slime/infra-fly` 等のプラグイン** として提供する方針（本体との依存関係を切り離す）。

> ……というのをいきなりgemini-3-pro-previewが言い出して、Claude 4.6 Sonnetも衝撃を受けて検討する価値があると纏めてくれました。実用レベルに達するかどうかはともかく、「FWがインフラを提示する」という発想が無かったのでたまげたなぁ。IaC時代の発想だと思った。（他人事）

### 欠点と補完案

**欠点：** レベルだけでは最適なインフラは分からない。アプリ規模Lv3でも100万ユーザーいれば別の構成が必要なように、**実際の負荷によって最適解が変わる**。レベル基準の推薦はあくまでテンプレートの提示にとどまる。

**補完案：メトリクスとの連携**

```bash
slime export:infra-context  # Level + メトリクスサマリーを1ファイルに出力
```

メトリクスから読み取れるボトルネックの例：

| メトリクス | 推論できること |
|--|--|
| 1回のWorkflowで同じstore関数が多数回呼ばれる | N+1。storeに一括取得の関数を足す |
| DBクエリ時間が高い | 読みレプリカ or Redisキャッシュの追加 |
| DB時間は正常だがレスポンスが遅い | アプリサーバーのスケールアウト |
| 特定エンドポイントへの集中 | CDN・エッジキャッシュの導入 |
| メモリ使用率の右肩上がり | インスタンスサイズアップ or メモリリーク疑い |

ただしSlime自身がメトリクスを解析してインフラを推薦する（＝FWがAIを呼ぶ）設計はしない。あくまで `slime export:infra-context` でLevel情報とメトリクスサマリーをファイルとして吐き出し、**AIエージェントがそれを読んで判断する**という構造を維持する。

### AWS向け実装の現状（2026年2月時点）

2026年2月、AWSが [Agent Plugins for AWS](https://aws.amazon.com/blogs/developer/introducing-agent-plugins-for-aws/)（`deploy-on-aws`プラグイン）をOSSとして公開した。このプラグインはClaudeCodeやCursor等のコーディングエージェントに「コードベースを解析して最適なAWSサービスを推薦→コスト試算→CDK/CloudFormation生成」を行うスキルを追加するMCPサーバー群で、まさにInfra-Slimeがやりたかった領域をAWS自身がカバーし始めている。

`slime export:infra-context` でSlimeのLevelとメトリクスをコンテキストとして吐き出せば、deploy-on-awsプラグインのAnalyzeフェーズがそれを読んでより精度の高い推薦を行える。**`@slime/infra-aws` を自前で実装・維持するより、deploy-on-awsプラグインにAWS側の判断を委ねてSlimeはコンテキスト提供に徹する方がコスパがいい可能性がある。**

**住み分けの方針：**
- Lv基準の軽量テンプレート生成（Dockerfile・docker-compose.yml）はプラグインの有無に関わらず有用なため残す
- 本格的なクラウド最適化は外部エコシステムに任せる
