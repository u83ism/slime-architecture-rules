# Webアプリ以外への落とし込み指針

> **位置づけ：** このリポジトリの設計論はWebアプリ（APIサーバー）向けで、そのままでは他の種類のプログラムに使えない。本書は、CLIツール・フロントエンドで完結するツール・ゲームなどに**落とし込むときの対応表と手順**をまとめる。
>
> **想定する使い方：** 別プロジェクトで「このリポジトリを参考に落とし込んで」と指示されたAIが、最初に読む資料。各Lvの詳細は[Lv別アーキテクチャリファレンス](./Lv別アーキテクチャリファレンス.md)（正本）を、設計理由は[補足資料](./Kaachan%26Slime%26Slime%20Architecture構想の設計根拠、補足資料.md)を参照する。
>
> **注意：** Slime FWのAPI（`route.group`・`json(...)`・`slime.auth()`・`withTransaction()`・`defer()` 等）とKaachanの検査は、他のプロジェクトには存在しない。持ち出すのは考え方と構造であって、FWの呼び出し方ではない。

---

## 1. 最初に見分けること：プログラムの形

この設計論は、次の2つを前提にしている。

- **1回呼ばれたら1回結果を返して終わる**（リクエスト→レスポンス）
- **状態はプログラムの外（DB）にある**。プログラム自体は呼び出しをまたいで状態を持たない

落とし込む先がこの前提を満たすかで、移しやすさが決まる。

| 形 | 例 | 前提との一致 | 移しやすさ |
|---|---|---|---|
| **呼び出し完結型** | CLIツール、バッチ、変換スクリプト、Lambda | 一致する | Lv5まではほぼ1対1で対応する |
| **常駐状態型** | フロントだけで完結するツール、エディタ、デスクトップアプリ、ターン制ゲーム | 一致しない。状態はメモリにあり、イベントが何度も届く | 原則は使えるが、**「状態の持ち主」という概念を足す**必要がある（3章） |
| **フレームループ型** | リアルタイムアクションゲーム、シミュレーション | 一致しない。毎フレーム状態を更新する | ルール判定の部分にだけ使う。全体の構造は別の流儀（ECS等）が主になる |

1つのプログラムに複数の形が混ざることもある（例：ゲーム本体はフレームループ型、マップ変換ツールは呼び出し完結型）。その場合は部分ごとに判定する。

## 2. 持ち出せる原則と、持ち出せないもの

### 2.1 持ち出せる原則

各Lvの道具を外すと、Webに依存しない原則が残る。落とし込みでは**この原則を守ることを目的にし、Webでの形は真似しない**。

| # | 原則 | Webでの形（出典Lv） | 一般化した形 |
|---|---|---|---|
| 1 | **境界でParseする**（Parse, don't validate） | `parse.ts` がリクエストを型付きの入力に変える（Lv3） | 外から来たもの（argv・設定ファイル・フォーム入力・インポートしたファイル・セーブデータ・ネットワークの応答）は、入口で一度だけ型付きの値に変える。内側は検証済みの型だけを扱う |
| 2 | **判断は純粋関数、副作用は外側**（Functional Core, Imperative Shell） | `logic.ts` が純粋、`workflow.ts` がStore・Clientを呼ぶ（Lv5） | 判断・計算・状態遷移は純粋関数に閉じ込める。ファイル・ネットワーク・時刻・乱数・描画は外側の進行役が担い、必要な値を引数で純粋関数に渡す |
| 3 | **業務上の拒否は戻り値で運び、境界で外向けの形に変える** | Result型の `err` をrouteまで返し、HTTPステータスとProblem Detailsに変える（Lv5） | 想定内の失敗は `Result` で返し、外側の境界で終了コード・UIのメッセージ・ログなどに変える。throwは想定外の障害（バグ・I/O障害）専用にする |
| 4 | **読みと書きを名前で分ける** | `query*` / `command*` の命名（Lv4）、command/queryフォルダ（Lv10） | 状態を変える関数と読むだけの関数を、名前で見分けられるようにする |
| 5 | **外部とのやりとりは差し替えられるようにする**（必要になってから） | `ports.ts` と `infrastructure/`、Portを引数で受け取る関数型DI（Lv9） | ファイルシステム・ストレージ・API・描画・音を型で宣言し、実装を引数で渡す。テストや別環境（ブラウザ/Node、本番/モック）で差し替えが必要になったら導入する |
| 6 | **小さく始めて段階的に育てる** | Lv1〜10 | 最初から完成形を作らない。ファイルが太ったら分ける。分けた理由を後から説明できる構造にする |

### 2.2 持ち出せないもの

| Webに固有のもの | 理由 | 代わりに考えること |
|---|---|---|
| route・HTTPメソッド・`/api` グループ | HTTPの概念 | 入口の振り分け（サブコマンド・画面・入力イベント） |
| Middleware（認証・CORS・レートリミット） | HTTPの関門の概念。ローカルで動くツールには関門がない | 多くの場合は不要。設定の読み込みや前提チェック程度が残る |
| プリンシパル・リソース単位の認可 | 複数の利用者を前提にしている | 不要なことが多い |
| トランザクション・`defer()`・Lv7のorchestrate/ | DBの原子性を前提にしている | 「保存は全部成功するか全部失敗するか」が必要な場面だけ、一時ファイルに書いてからリネームする等で個別に対処する |
| Lv6のドメインフォルダ分割 | 業務ドメインが複数ある規模を前提にしている | 個人のツールはLv3〜5で収まることが多い。ゲームは業務ドメインではなくシステム（描画・物理・AI）で分かれる |
| Lv10のCQRS（読み書きでDBモデルを分ける） | DBを前提にしている | 「状態から表示用の値を導く関数（selector）」として小さく効く |

## 3. 足りない概念：状態の持ち主（常駐状態型・フレームループ型）

Webアプリでは、状態の正本はDBにある。そのためLogicとStoreは呼び合わず、Workflowが「Storeから読む → Logicに渡す → Storeに書く」を1回のリクエストの中で行う。

常駐するプログラムでは、状態の正本は**メモリ上の状態**になる。そこへイベントが届き続け、画面は状態から導かれる。この形はElm Architecture（Model / update / view）として知られている。

```
イベント → update(state, event) → [新しいstate, 実行してほしい副作用] → view(新しいstate)
                                              ↓
                                       進行役が副作用を実行し、結果を新しいイベントとして戻す
```

この設計論の要素に当てはめると、次のようになる。

| この設計論 | 常駐状態型での形 |
|---|---|
| Logic | `update`（状態遷移の純粋関数）。業務上の拒否は `Result` で返せる |
| Workflow | 副作用の実行役（fetch・保存・タイマー）。結果をイベントとして `update` に戻す |
| Store | 永続化（localStorage・IndexedDB・ファイル）。**正本ではなく保存先**になる |
| （新しく足すもの） | **状態の持ち主**。現在の状態を1か所で保持し、イベントを `update` に渡して差し替える。React なら `useReducer`、ゲームならループ本体がこれにあたる |

Webアプリの「logicとstoreは呼び合わない」は、ここでは**「状態は持ち主が持ち、logicには引数として渡す。logicは状態を直接書き換えず、新しい状態を返す」**に置き換わる。

## 4. 種類別の落とし込み

### 4.1 CLIツール（呼び出し完結型）

コマンド1回の実行が1リクエストにあたる。Lv1〜5の構造がほぼそのまま使える。

| この設計論 | CLIでの形 |
|---|---|
| route | サブコマンドの振り分け（`main.ts` / `cli.ts`） |
| middleware | ほぼ不要。設定ファイルの読み込みや、必要なツールが入っているかのチェック程度 |
| parse | argv・環境変数・設定ファイル・入力ファイルを型付きの入力に変える |
| workflow | コマンドごとの進行役 |
| logic | 変換・判定・計算の純粋関数 |
| store | ファイルシステムの読み書き |
| client | 外部API・子プロセスの呼び出し |
| 応答形式（Lv5の `json(...)`） | 出力の形式（人間向けテキスト・`--json`・表）と終了コード |

```
src/
  cli.ts        # サブコマンドの振り分け。parseとworkflowを組み合わせ、結果を出力と終了コードに変える
  parse.ts      # argv・設定ファイル → 型付きの入力
  workflow.ts   # コマンドごとの進行役
  logic.ts      # 純粋な判定・変換
  store.ts      # ファイルの読み書き
  errors.ts     # 想定内の失敗のコード（型のみ）
```

```ts
// errors.ts — 全コードに終了コードを対応させる（漏れは型エラー）。slime.config.ts の errors と同じ考え方
export const exitCodes = {
  INPUT_NOT_FOUND: 2,
  ALREADY_CONVERTED: 3,
} satisfies Record<ConvertErrorCode, number>

// cli.ts — 境界で Result を出力と終了コードに変える
const result = await convertWorkflow(parseConvertArgs(argv))
if (!result.ok) {
  console.error(messages[result.error])
  process.exit(exitCodes[result.error])
}
print(result.value, { json: flags.json })
```

### 4.2 フロントエンドで完結するツール（常駐状態型）

3章の形をとる。

| この設計論 | フロント完結ツールでの形 |
|---|---|
| route | 画面の振り分け（ルーター）と、UIイベントからアクションへの変換 |
| middleware | 不要 |
| parse | フォーム入力・インポートしたファイル・URLパラメータ・localStorageから読んだ値を型付きの値に変える。**保存データの読み込みも境界として扱う**（古い形式のデータが来ることがある） |
| workflow | 副作用の実行役（fetch・保存・ファイル書き出し） |
| logic | `update`（reducer）と、状態から表示用の値を導く関数（selector） |
| store | localStorage・IndexedDB（保存先であって正本ではない） |
| 状態の持ち主 | `useReducer`・状態管理ライブラリのstore |
| Lv8 ドメインイベント | `update` が「起きたこと」を戻り値で返し、通知表示・保存・ログが受け取る形で使える |

```ts
// logic.ts — 状態遷移は純粋関数。想定内の拒否は Result で返す
export const todoCanAdd = (state: State, title: string): Result<State, "TITLE_EMPTY" | "TOO_MANY"> =>
  title.trim() === "" ? err("TITLE_EMPTY")
  : state.todos.length >= 100 ? err("TOO_MANY")
  : ok({ ...state, todos: [...state.todos, newTodo(title)] })
```

UIコンポーネントは `view` にあたる。コンポーネントの中に判断を書かず、logicを呼んで結果を表示する。

### 4.3 ゲーム

ゲームの種類で移しやすさが大きく変わる。

**ターン制・パズル・カードゲーム（常駐状態型）**

純粋関数のLogicと相性がとても良い。同じ状態と入力から同じ結果が出るので、リプレイ・アンドゥ・テスト・AI対戦相手の先読みがほぼタダで手に入る（乱数は引数で渡すか、シードを状態に含める）。

| この設計論 | ターン制ゲームでの形 |
|---|---|
| route | プレイヤーの入力 → アクション（「カードを出す」「移動する」）への変換 |
| parse | セーブデータ・マップ定義・カード定義などのデータファイルの読み込み |
| workflow | ターンの進行役。演出の再生を待ち、次の入力を受け付ける |
| logic | ルール判定（`cardCanPlay` 等）と状態遷移 |
| Lv4 command命名 | アクションをデータとして表す（Commandパターン）。アンドゥ・リプレイの記録になる |
| **Lv8 ドメインイベント** | **相性がとても良い**。状態遷移が「ダメージを与えた」「ユニットが倒れた」をイベントとして戻り値で返し、演出・効果音・実績解除が受け取る。ルールの関数が演出を知らずに済む |
| Lv9 ports | 描画・音・入力・セーブ先の差し替え（テストではモックにする） |

```ts
// logic.ts — ルールは演出を知らない。起きたことをイベントで返す
export const applyAttack = (state: Battle, attackerId: Id, targetId: Id): Result<[Battle, BattleEvent[]], "OUT_OF_RANGE"> => { /* ... */ }

// workflow.ts — 進行役がイベントを演出に流す
const result = applyAttack(state, a, t)
if (!result.ok) return showHint(result.error)
const [next, events] = result.value
await playEffects(events)   // 「ダメージを与えた」→ 数字のポップアップ、「倒れた」→ 消滅演出
setState(next)
```

**リアルタイムアクション・シミュレーション（フレームループ型）**

- 毎フレーム状態をイミュータブルにコピーすると、性能面で厳しいことが多い。状態をその場で書き換える前提の構造（ECS：Entity Component System 等）が主流で、分け方の軸も業務ドメインではなくシステム（物理・描画・AI・入力）になる
- そのため、この設計論の構造は全体には使わない。**ルール判定の部分**（ダメージ計算・当たり判定の後の処理・スコア計算・ステートマシンの遷移条件）だけを純粋関数として切り出す
- 原則1（境界でParse）と原則5（差し替え可能なI/O）は、そのまま効く

## 5. 落とし込みの手順（AI向け）

別プロジェクトで落とし込みを頼まれたら、次の順に進める。

1. **プログラムの形を判定する**（1章）。部分ごとに形が違えば、部分ごとに判定する
2. **持ち出せる原則（2.1）を、そのプロジェクトの言葉で書き直す**。「Workflow」「Logic」などの名前を使うかどうかは、そのプロジェクトの既存の命名に合わせる。この設計論の用語を押しつけない
3. **持ち出せないもの（2.2）を捨てる**。Middleware・route・トランザクションなどを、無理に対応物を作って残さない
4. **常駐状態型なら、状態の持ち主を決める**（3章）。どこが状態を保持し、どこが更新し、どこが保存するか
5. **規模に合ったLvで止める**。個人のツールはLv3〜5相当で十分なことが多い。Lv6以降は、明確に独立した関心事が複数あるときだけ検討する
6. **守る規約をプロジェクトのルール（CLAUDE.md等）に書く**。Kaachanは存在しないので、自動検査の代わりに文章で残す。最低限、次の2つを書く
   - 判断・計算の関数は副作用を持たず、ファイル・ネットワーク・時刻・乱数・描画に触れない
   - 外から来たデータは入口で型付きの値に変え、内側では検証し直さない
7. **判断の関数にテストを書く**。純粋関数にしたことの一番の見返りがここ（Lv7でLogicのテストを義務化したのと同じ理由）

## 6. 種類別の対照表（まとめ）

| この設計論 | CLI | フロント完結ツール | ターン制ゲーム | リアルタイムゲーム |
|---|---|---|---|---|
| route | サブコマンドの振り分け | 画面・イベントの振り分け | 入力 → アクション | 入力システム |
| middleware | ほぼ不要 | 不要 | 不要 | 不要 |
| parse | argv・設定・入力ファイル | フォーム・インポート・保存データ | セーブ・データ定義 | セーブ・データ定義 |
| workflow | コマンドの進行役 | 副作用の実行役 | ターンの進行役 | ゲームループ |
| logic | 判定・変換 | update・selector | ルール判定・状態遷移 | ルール判定だけ切り出す |
| store | ファイルシステム | localStorage・IndexedDB | セーブ | セーブ |
| 状態の持ち主 | 不要 | `useReducer` 等 | ゲーム本体 | ECSのワールド等 |
| Result の変換先 | 終了コード・エラー出力 | UIのメッセージ | ヒント表示・入力の却下 | （使う場面は少ない） |
| Lv8 イベント | ほぼ不要 | 使える | とても相性が良い | 使える（イベントキュー） |
| Lv9 ports | テスト用に必要なら | ブラウザ/Nodeの差し替えに | 描画・音・入力の差し替え | 描画・音・入力の差し替え |
| 止まる目安 | Lv3〜5 | Lv5 + 状態の持ち主 | Lv5 + 状態の持ち主 + イベント | 原則だけ使う |
